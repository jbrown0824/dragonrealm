# Dragon Realm

A Roblox game where every player is a dragon. It's a Rojo project and **everything is generated in code**: the map, the dragons, the vikings, the animals and the UI. There are no meshes, models or Studio-built assets. The README covers features and controls; this file covers how to work on the code.

## Workflow

- The user playtests in Roblox Studio. **You can't run Roblox here**, so do all your checking offline (see below), then ask the user to playtest and paste errors from the **Output** window.
- Build the place file: `rojo build default.project.json -o DragonRealm.rbxlx`. It's git-ignored, so rebuild after every change. The user opens it in Studio, or live-syncs with `rojo serve`.
- Git remote: `git@github.com:jbrown0824/dragonrealm.git`, branch `main`. Pushing works through the user's SSH key. The `gh` CLI isn't installed, so you can't create repos. **Commit and push only when the user asks.**
- Tools (Homebrew): `rojo`, `luau`, `luau-analyze`, `luau-compile`. Python 3 has numpy and Pillow.

## Checks (run before telling the user something works)

```
tools/checks/run_all.sh     # lint, xref, logic tests, place build
tools/sim/run.sh            # boots the real server + client in a simulator and plays the game
```

`run_all.sh` runs nine things:
1. Compiles every file and runs `luau-analyze`, filtering out noise about Roblox globals and types it doesn't know. Anything left (an unknown global, a shadowed local...) fails the run: a missing forward declaration once slipped through as an "unknown global".
2. `glyph_check.py`: no characters Roblox can't draw (Unicode 12+ emoji like 🪨, and symbols like ✕ ● ○). They show up as empty boxes in game.
3. `xref.py`: every `S.Service.fn` (server) and `App.Module.fn` (client) call, `Remotes.event/func("Name")` name and require path must actually exist. The analyzer can't see these because services are wired together at runtime. Module tables must be named like their file (a UI module `Pets.luau` returns `Pets`; alias a same-named config, e.g. `PetInfo`).
4. `logic_test.luau`: data-consistency tests for the shared modules (talent trees, abilities, items, quests, zones, potions, pets and pet levels, treats, villagers and their walking graph, animals, food, hunger, live tuning, balance table).
5. `walk_check.py`: builds the world offline and checks every straight walk a villager can take (`Zones.TownWalk`, each house door, up the ramp and between the indoor spots) and the raiders' walk from the beach (`Raids.Landings`) against the solid parts. Move a stall, lamp or piece of furniture and this tells you if you blocked a route.
6. `water_check.luau`: every lake, the river and the channels (`Zones.Streams`) are deep enough, never hang over the void, and the longships have water under their whole hull.
7. `dungeon_check.luau`: carves every dungeon interior on the mock terrain and checks there's a floor with headroom under every marker (entrance, way out, monsters, bosses, hoard), and that every edge of the `DungeonNav` graph (tunnels, each room's way to its tunnel mouths and monsters, the spiral ramp and the dungeon's extra `routes`: bridges, ledges) is walkable: no step over 2.6 studs, 9 studs of headroom. It also checks the graph is connected, that no monster, boss, keeper or hoard spot is in lava, that packs are `PACK_SPACING` apart, that patrol routes can be walked, that every boss room has doors, that a rune shield's guard `spots` are on the room's floor (out of lava, off the ledge, a straight walk from the middle), that the Way out signs are up, and that each cave mouth in the viking lands is open (no terrain across the doorway, the passage or the way up to it: `DungeonBuilder.MOUTH`) with its hill behind it. (The mock indexes terrain edits in buckets: call `TERRAIN_PREPARE()` again after building more terrain.) Rooms that aren't safe to cross straight through (the Forge's lava river and shaft) set `hub = false` and list their `routes`. With a `DUNGEON_MAP = "<id>"` header it prints the floor instead, for `tools/preview/dungeon_map.py`'s top-down PNG.
8. `gui_check.sh`: runs the real client in the simulator at desktop (1280×720) and phone (844×390, touch) size, dumps the main screens (HUD for a new dragon and a veteran, pets, eggs folded and unfolded, the hatch reveal, "need gold" and the Store at its gold packs, store, collection, skill tree with and without the Learn bubble, shops, map, raid bar, shops closed, range window and session panel, the Dungeons window, the queue pill, a ready check, the run tracker and the map inside a dungeon) and renders them with `tools/preview/gui_render.py`. It fails on client errors, text that overflows its box, or panels off the screen. **Look at the PNGs** in `tools/preview/_gui_desktop` and `_gui_phone` after any UI change.
9. Builds the place file.

## Conventions

- **Server services** are modules that return a table with `init(services)` (store `S`, set up state) and `start()` (connect remotes, run loops; always called with `task.spawn`). They call each other as `S.PlayerService.x(...)`. A new service must be added to `ORDER` in `src/server/init.server.luau`.
- **Client modules** get the shared `App` table in `init(App)`. A new module must be added to `src/client/init.client.luau`.
- **Remotes**: every name is listed in `src/shared/Remotes.luau`. The server is authoritative: clients send intents (cast, buy, plant...) and the server validates cooldowns, range, gold and ownership. Vendors check range with `S.ShopService.isNear(player, { shopId })`.
- **Stats**: anything that changes stats outside gear and talents (potions, pets, hunger) goes through `BonusUtil.entries(profile)` so `PlayerService.recompute` and the tests agree. Balance numbers that the admin panel tunes go through `Tuning` inside `StatCalc`.
- **Stalls** that open a window (not a gear shop) use a `PanelPrompt` tag with a `Panel` attribute; the server fires `OpenPanel` and `init.client.luau` opens the window.
- **Profile fields**: add new fields to `defaultProfile` in DataService; `reconcile` fills them into old saves. Migrate changed shapes on load (see `FarmService.migratePlant`) and add the old shape to the sim's save test.
- **UI** is built in code with `Theme.make/label/button/window`, designed for a 1100×700 screen and scaled with UIScale. Windows also get a "Fit" UIScale when they'd be too big for the screen. The desktop HUD's top-right column is: minimap (y 10-190), zone name, then the quest tracker (y 236+); the menu buttons sit to its right. The 💎 🎁 ❓ buttons are in the unscaled `TopBar` gui, in Roblox's top bar row.
- **Phones** (`Windows.mobile`: touch, no keyboard): `HUD.mobileLayout` moves the ability buttons into the unscaled `Touch` gui (screen points, placed around Roblox's jump button: 70pt at 95 from the right and 90 from the bottom on small screens), puts the bars at the top, the menu in a 2-column grid on the left, a smaller minimap at the edge, and toasts at the top center. Small screens get a larger HUD scale. Check both sizes with `gui_check.sh` when you touch the HUD.
- **Messages in windows**: use `App.Windows.notify(text, color, icon, action?)`: it shows in the open window's status banner (toasts sit behind windows), or as a toast when no window is open. The banner sits just below the window (`Windows.placeBanner`), or on its title bar when the screen is too short, never over the content. `action` ({ text, color, onClick }) adds a button to it.
- **Red count badges** (Skills: unspent points; Pets and the Eggs tab: eggs waiting) use `Theme.badge` / `Theme.setBadge`.
- **Passes** are asked about through `StoreService` (`hasPass`, `xpMultiplier`, `goldMultiplier`, `flightMultiplier`); pass ownership can change mid-session, so anything that feeds stats calls `PlayerService.recompute` when a pass turns on. "Handy" passes (`handy = true`) get their own Store section.
- **Places** (`Zones.places()`) are the one list of named spots: the world map's list and the Wayfinder teleports (`TeleportTo`, checked on the server). Add new destinations there.
- **Egg-only species**: a pet with `egg = "<eggId>"` only hatches from that egg; eggs roll species with `Pets.speciesFor(eggId, rarity)`, never `speciesOfRarity` directly.
- **Robux nudges stay polite**: nothing opens the Store by itself. A buy button you can't afford stays dimmed; `Theme.onDisabledClick(button, fn)` with `App.Store.needGold(cost)` puts a "Get gold" button in the window's message instead. Use that for new gold purchases.
- **Text glyphs**: use emoji or plain ASCII in UI text. Symbol characters like ✕ ▲ ● − ↺ ✔ can render as empty boxes in Roblox fonts (the old close button did). Draw shapes (pips, arrows) with Frames instead.
- **Map data**: roads, trails, lakes, the river, camps and shops all come from `Config/Zones`, which both the world builder and the map UI read. Add new places there so they show up on the map.
- **Balance numbers** belong in `src/shared/Config/`, not in service code.
- **Robux**: products are granted only in `StoreService` (ProcessReceipt records the receipt id on the profile and saves before returning PurchaseGranted). Never grant paid items anywhere else. Ids live in `Config/Store`; with an id of 0, Studio grants items free for testing (`StudioPurchase` refuses outside Studio).
- Match the existing style: tabs, typed function parameters, and short header comments explaining *why*.

## Gotchas (learned the hard way)

- **`CanQuery = false` only works when `CanCollide = false`.** Solid invisible walls still block raycasts. That's why barriers (world bounds, arena walls and ceiling) live in `workspace.Barriers`, outside `workspace.Map`: services raycast against Map + Terrain only. The boss once spawned on top of the arena ceiling because of this.
- Spawn points use `terrainGround` plus `EnemyService.isGoodSpawn` (not water, not inside a prop), so vikings and animals don't land on roofs, tents or lakes. `groundAt(pos, fromAbove)` casts from just above a point.
- **Signs** use `Props.sign`, which raycasts the terrain and lifts the board so its bottom clears the ground by 3.5 studs. Low signs used to sink into hills and banks. Anything placed on uneven ground should use `Props.groundY`.
- **Water**: lakes and the river are carved as round air "basins" and then `ReplaceMaterial(Air → Water)` below `Zones.WATER_LEVEL` (-4). Keep water regions inside the ground block (x ±660) or the fill spills into the void. The ground block is only 16 studs thick, so `Wilds.lakeBed` fills mud down to -44 under every lake and the river first; without it, deep bowls punched through and left water hanging over the void. `water_check.luau` guards all of this.
- **Per-player state on shared objects** (camp chests): the server keeps a player attribute (`ChestReady_<campId>`, server time) and each client draws the lid, treasure and prompt from its own attribute in WorldView. Local changes to replicated instances only affect that client.
- **Villagers** live in `workspace.Civilians` (outside Map, so attacks and service raycasts ignore them), use the `Dragons` collision group (they never block players), and hop to the next node if a walk takes too long. Their routes are data in `Zones.TownWalk`; keep them clear (`walk_check.py`).
- **Services find world objects by tag, name and attribute**, so keep these if you rework the map: tags `PlayerBase`, `ShopPrompt`, `PanelPrompt`, `DungeonDoor`, `DungeonJoin`, `DungeonChest`, `DungeonFood`, `DungeonExit`, `QuestPrompt`, `QuestGiver`, `Dragon`, `Civilian`, `Viking`, `Animal`, `CampChest`, `TrainingDummy`, `FishingSpot`, `Lamp` (street lamp glass, lit at night), `PracticeTarget`; names `Plots/Plot1..12`, `HomeSpawn`, `BotDock`, `Sign` (with a SurfaceGui `Title`), `WarHornPrompt`, `Town/House1..10` (RaidService burns them), `Town/Well1..2` (with a `WellTag` sign RaidService lights), `Town/<shop id>` (stalls), chest parts `Base`, `Lid` (a model), `Treasure` (a model), `Glow`; attributes `BaseIndex`, `OwnerUserId`, `ShopTab`, `Panel` (incl. `Range` on the firing mats, with `Lane`), `GiverId`, `CampId`, `SpotId`, `Kind` (Dummy/Golem), `PlotIndex`, `Fire` / `BurnsAt` on houses.
- **Prompt filtering is client-side** (WorldView): a prompt with an `OwnerUserId` only shows for that player; farm prompts also carry an `On` attribute (the server's wish) and only show on the plot you're facing. Set both when you add owner-only prompts.
- **Dragon rig**: the Motor6D names (`BodyJoint`, `Neck1..n`, `Head`, `Jaw`, `LidL/R`, `WingL/R`, `WingL2/R2`, `LegXX`/`KneeXX`, `Tail1..n`, `Frill`) and the model attributes `RigNeck/RigTail/RigLegs/RigCurl/RigFrill/DragonScale` are the contract between DragonBuilder, DragonRig, the Animator and PetFollow. Models are built facing -Z, spread for gliding; all joint frames are world-aligned. Animal rigs use `LegFL/FR/BL/BR`, `Head`, `Tail`.
- Player dragons are custom Humanoid rigs (R15 rig type, manual `HipHeight`, `CharacterAutoLoads = false`, spawned by `PlayerService.spawn`). The client owns its dragon's physics, so flight and dash run client-side in `Movement` (flight speed × the `FlightSpeedMult` character attribute).
- **Anything you parent to PlayerGui** (ScreenGuis, and BillboardGuis like quest markers and the waypoint pin) needs `ResetOnSpawn = false`, or Roblox deletes it every time the dragon respawns. The quest ❗/❓ markers vanished after a death this way. The mock clears PlayerGui on a new character too, and the client sim checks the markers survive a respawn.
- Tween completion: connect `tween.Completed` **before** `tween:Play()`.
- **Pets** are drawn by each client from the character's `Pets` attribute: `species:level:golden` entries, comma-separated (PetService.applyToCharacter). Pet records are `{ uid, species, level?, golden? }`; a missing level means 1.
- **Limited stock** is per player and saved (`profile.shopStock`); vendors call `S.StockService.left/take`. Gear rows store slot and rarity only; the item is made at the buyer's current level.
- **Paragon**: past the level cap `profile.xp` fills `profile.paragon`. Anything that counts skill points must pass the paragon (`TalentUtil.available(level, talents, paragon)`).
- **Part shapes**: `Shape = Ball` forces a part to a sphere. For an ellipsoid use a block with a `SpecialMesh` of type Sphere (`Props.ellipsoid`).
- `Workspace.StreamingEnabled` is off (the project file sets it), so clients can assume the whole map exists.
- DataStores are skipped in Studio unless API access is enabled; `DataService` falls back to a fresh profile each session. Saved plot arrays use `false` for empty slots, never `nil` holes. Players whose save predates the tutorial skip it.
- **Admin code** lives in `src/server/Config/AdminConfig.luau` (default `DRAGONLORD`). Remind the user to change it or set `ALLOWED_USER_IDS` before publishing.
- **Day/night** is computed, not streamed: `shared/DayNight` turns server time plus the workspace attribute `DayOffset` into the clock, and each client's `Sky` sets `Lighting.ClockTime` every frame. Never set `ClockTime` from the server. Services that care listen to `DayNightService.nightfall` / `daybreak`.
- **Raiders** are ordinary EnemyService vikings with `raid = true` (they may fight and hurt dragons inside the safe town: `targetRoot` skips the safe check and their hits pass `ignoreSafe`) and an `objective(e, t)` that runs whenever no dragon is in reach: a goal (house, villager, dragon, roam) picked by RaidService. They drop dragons past `Raids.CHASE_RANGE`, ignore (or throw at) dragons flying above `Raids.FLYER_HEIGHT`, and only the `Raids.CROWD` closest keep after one dragon (`EnemyService.raidersOn` counts targets and `hunting`). They board the longships as real raiders: welded to the keel by their root, parented to the ship, `customAI` (no thinking) and `keepBody` while `e.aboard` (model attribute `Aboard`: the Animator makes them cheer), so dragons can fight them on the way in; one beaten on deck or mid-leap goes `overboard` (RaidService) instead of toppling. They count toward `RaidLeft` from boarding, leap ashore in an arc (`Leaping`) and only then start thinking; the ships row back out between waves. `RaidService.raiders()` is only the ones ashore (villagers and quest givers ignore the ships), `RaidService.aboard()` the ones on deck. After a lost raid nothing vanishes: the raiders still standing run back to the beach with loot sacks (`runBack`, `customAI`), leap aboard and row away. They route along `Zones.TownWalk` through `CivilianService.route`, and to lairs via `Zones.LairApproach` (the lair signs hang high so they can walk in under them), so keep raider routes in `walk_check`. Raid state reaches clients as workspace attributes (`RaidPhase`, `RaidLeft`, `HousesBurned`, `ShopsClosedUntil`...), and every town vendor checks `ShopService.closedMessage()`. Villager and quest giver fire goes through RaidService's `puff`, which respects `RaidService.villagerFloor(e)` (it wears away with `e.landedAt`) and `Raids.villagerHelp(dragons online)`; quest givers turn by `PivotTo` and are put back when the raid ends.
- **Fire and water**: dragons can't beat flames out. RaidService's water tick (5 times a second, only while there's a raid or a fire) fills a dragon to `Raids.WATER_LOADS` (player attribute `Water`, a number that runs down while pouring, plus a `WaterDrips` emitter on its root) when there's terrain water just below its belly or it's at a town well (`Zones.Wells`, built by `Props.well`). A dragon with water hovering over a burning house pours (`Pouring` attribute, `WaterPour` emitter): each tick adds to the house's `h.douse` (0-1, shared by every dragon pouring; `RaidService.douseProgress`), `soak` shrinks the flames and turns the smoke to steam, and at 1 `putOut` → `extinguish` → `fadeOut` lets the flames die away before the steam clears (a fire left alone creeps back after `Raids.REGROW_DELAY`). A house burning down is animated on the server (`collapse`: flare-up, soot creeping over the walls, the roof caving in with the ridge beam and its carved heads as one rigid piece, the flames dying down to embers); `remember` keeps every part's colour, material and CFrame so the rebuild puts it all back. Effects live in a `FireFX` folder inside the house model, which `remember` skips. Villagers don't go into burning or burned houses.
- **Raiders on deck** take `Raids.DECK_DAMAGE_TAKEN` of the damage: `CombatService.damageEnemy` multiplies by `e.damageTakenMult`, and the model attribute `Shielded` puts a 🛡️ in the nametag's status icons.
- **The raid's clock** is its own (`r.endsAt` = landing + the waves + `Raids.FIGHT_TIME`), not dawn: `daybreak` never ends a raid.

- **Downed dragons**: a knocked-out villager or a dead player dragon is anchored and lowered onto its belly by `WorldUtil.layDragon` (`standDragon` undoes it), and clients pose it with DragonRig's `"downed"` mode (model attribute `KnockedOut`, or Humanoid health 0). Dead vikings topple over in `EnemyService.kill` (root anchored, the body tipped round its feet) and vanish with a puff 3 seconds later; animals have their own carcass pose (WildlifeService).
- **Dungeon interiors** are carved into Terrain far off the map (`Dungeons.origin(id, slot)`: x -3200 and beyond, one slot per run at a time, built lazily and reused), under `workspace.Map.Dungeons`. Floors are **terrain**, so `terrainGround`, `isGoodSpawn` and the mock's straight-down raycasts work; walls and ceilings are terrain too (and decor parts), so a cast from high above hits the ceiling. Use `DungeonBuilder.floorAt(pos)` (it casts from just above the point) and pass `opts.ground` to `EnemyService.spawn`. Rooms, tunnels, ramps, bridges, ledges and the spiral are data in `Config/Dungeons`: keep them walkable (`dungeon_check`). The mock's `FillBlock` intersects tilted blocks exactly, so a tilted block is a ramp there too.
- **Who is in a run** is the player attributes `InDungeon` (dungeon id) and `DungeonRun` (run id); ask the server with `S.DungeonService.inRun(player)`. Run monsters carry `e.run` and only target dragons with the same `DungeonRun` (`EnemyService.targetRoot`), pull their whole `e.pack` (`DungeonService.pullPack`), keep `e.lastCombat` (hits either way) and walk home without the instant heal (the run's tick regenerates them slowly, and evades one that's stuck: `EVADE_TIME` with no hit either way and no progress toward its target). The run's tick also pulls idle monsters within `ASSIST_RADIUS` of a fight, burns monsters in lava, steps patrol posts, drops draughts in boss fights and puts down a dragon hovering too high. Their rewards go to `DungeonService.rewardees(e)`. In a run: `ZoneService` skips the map bounds (zone `Dungeon:<id>`), `getSpawnCFrame` uses `DungeonService.spawnCFrame`, TeleportHome / Wayfinder / the boss queue refuse, and world boss and raid news (`BossService.announce`, RaidService's broadcast and defenders) skip the player. The client hides BossUI and RaidUI, and Sky switches to cave lighting, from `InDungeon`.
- **Death in a dungeon**: PlayerService's Died hook asks `DungeonService.onPlayerDied(player)`; true means no timed respawn and `Died` fires with -1 (the client's death screen shows "waiting for your group" and a Leave button). The run revives the dead beside a living member once the group is out of combat, and after a wipe resets engaged packs, heals the bosses and respawns everyone at the entrance.
- **Dungeon navigation**: `shared/DungeonNav` turns a dungeon's config into a graph (tunnel points, the middles of rooms with tunnel mouths, `routes`, spiral samples) and answers `route` (A*), `direct`, `inHazard` (a bridge deck is safe) and `crossesHazard`, all in the dungeon's own coordinates. Every run monster's walk goes through `EnemyService`'s `walkTo`, which asks `DungeonService.steer(e, goal)` for the next stop, so vikings take the bridges and the spiral and stop at the edge of lava. `dungeon_check` walks every edge of the same graph. Idle behaviour is `idle` on the mob def (`stand` or `wander`, via `DungeonService.idleSpot`) or `patrol = { points }` on a pack. The mock's Humanoids never move (`MoveTo` only records `_moveTo`), so sim checks look at goals, not positions.
- **Flying in a run**: the client caps flight at `Dungeons.HOVER_HEIGHT` over the floor (`Movement`'s `lowCeiling`) until the player attribute `DungeonCleared` is set; the server's run tick is the fallback. Run monsters' melee reach includes the hover height. Out-of-combat regen is skipped while `DungeonService.inCombat(player)`, and hunger doesn't drain in a run.
- **Boss doors**: `DungeonBuilder` puts doors where a tunnel enters a boss room (`roomMouths`), in `workspace.Barriers/DungeonDoors_<id>_<slot>` (outside Map: they're solid). Each has a `DungeonDoor` prompt and a `DungeonJoin` one ("Join the fight", only while sealed: it puts a run member outside the room just inside it); `DungeonBuilder.setDoor(door, "closed" | "open" | "sealed")`. Nothing fights through a shut door: `DungeonService.doorBetween(runId, a, b)` gates `EnemyService.targetRoot` and `CombatService.collectTargets`. Opening one calls `CombatService.breakStealth` and pulls run monsters within `DOOR_ALERT`; the mini-boss room's door nearest the entrance opens by itself once its `miniBoss.autoOpen` packs are beaten; a boss engaging seals its room's doors `SEAL_DELAY` later, its death opens them for good, an evade or wipe lifts the seal. A boss's participants are the dragons inside its room, and it evades only when none has been in its room for `EVADE_TIME` (a boss behind a rune shield takes no hits, so "no hits" isn't a reason). Participants get the player attribute `InBossFight` (world bosses set it too), which PetFollow uses to hide other dragons' pets. Rooms with 2+ tunnel mouths get a `WayOutSign` over the one nearest the entrance.
- **Dungeon bosses** are BossKit brains (`BossKit.new/think/use/reset`) driven by `Dungeons.Bosses` data: `moves`, and traits DungeonService handles (`summons`, `enrage`, `phases` with a rune `shield`, `secondLife` through `e.onLethal`, which `CombatService.damageEnemy` calls instead of killing). `e.immune` makes damage show as "immune" (and still counts as combat). `brain.hold` makes a boss cast from where it stands (Sigrun behind her shield). A rune shield's guards come in at `shield.spots`; one that's stuck or lost in the rock is put back at its spot (`unstick`), and `STUCK_KILLS` in a row kill it; a shield also gives out after `SHIELD_MAX_TIME`, so no fight can hang. Anything that unanchors an enemy root goes through `WorldUtil.release` (unanchored roots fall back to automatic network ownership: a client simulated Haldor into the floor). The Harpoon reels its victim in over `REEL_TIME`: the victim's client drags its own dragon (`Movement.reel`), everyone draws the chain (VFX `harpooned`), and the server only snaps a dragon that didn't arrive. Viking legs are a thigh and a shin (`LegL/R`, `KneeL/R`), so the Animator can sit and kneel them properly. World bosses use the same BossKit moves. Haldor's poses are server-set (`seat`, `standUp`, `kneel`: anchored, model attribute `Pose` = `sit`/`kneel`, which the client Animator draws) and his second life's look is `unbind`/`rebind` (model attribute `Unbound`). Whirlwind's small cyclones follow `Dungeons.cyclonePos`, which the server (damage) and the client (VFX `cyclones`) both use. The elder dragon's chains (`built.chains`) burst apart when Sigrun dies (`breakChains`) and are put back, hidden, for `resetSlot` to show the next group.
- **The level gap** (`Game.LEVEL_GAP`, `StatCalc.levelGap(diff)`, admin Tuning `levelGapLinear/Curve/Cap`): `CombatService.damageEnemy` multiplies a dragon's hit by it (attacker level - monster level) and `damagePlayer` a monster's (`opts.sourceLevel` - dragon level). Pass `noLevelGap` for damage that shouldn't care (the world boss arena: `e.arena`; the sparring golem); training dummies and PvP skip it. Levels and gear are tuned together: each class's per-level growth (Config/Classes) and `Items.POWER_BASE` / `POWER_PER_ILVL`, and logic_test pins at-level Rare totals near the old ones plus a level-up's worth.
- **Lifesteal and regen caps**: gear (relic `special` stats, flat, not scaled by item level) and pets (BonusUtil entries with `extra = true`) fill an "extra" bucket capped at `Game.EXTRA_LIFESTEAL_CAP` / `EXTRA_REGEN_CAP`; talents plus that bucket are capped at `LIFESTEAL_CAP` / `REGEN_CAP`. All four go through `StatCalc.caps()` and the admin's Tuning `caps` keys. Dungeon tuning is `Tuning.dungeon(id, key)` (`mobHp`, `mobDmg`, `bossHp`, `bossDmg`, `loot`) plus the global `groupScaling`.
- **Dungeon world objects**: the cave entrances live in `Map/DungeonEntrances` (each a mouth in a terrain knoll: the hill must stay behind the arch, `dungeon_check` makes sure the doorway is open) (each with a `PanelPrompt`, `Panel = "Dungeons"`, and a `DungeonId` attribute that ShopService passes on in `OpenPanel`); inside, the way out is a prompt tagged `DungeonExit`, the hidden hoard is a `Props.chest` model tagged `DungeonChest` (with `CampId` `Hoard_<id>_<slot>` and `OneTime`; it pays each dragon in the run once, and each client draws it open from its own `ChestReady_<CampId>` attribute, which a new run clears), the provisions table is tagged `DungeonFood` (eat once a run), and the boss doors are tagged `DungeonDoor`. The entrance keepers (Ylva, Kael) are quest givers with `dungeon` set: they don't fight raids and keep giving quests during one. They also stand inside their dungeon (`keeper = { at, face, food }`, built with `WorldUtil.questGiver`); `QuestService.nearGiver` accepts that spot through `DungeonService.keeperPosition`. The first clear of each dungeon pays `FIRST_CLEAR_XP` bars of XP, later ones `BOSS_XP`.
- **Dungeon eggs and relics** (`Pets.Eggs[...].dungeon`, `Items.Uniques[...].dungeon`) only come from their dungeon's boss (quest-only relics have `quest`). The eggs have no price: the Eggs tab lists them with where they drop instead of a Buy button. Pet stats in `Pets.FIXED_STATS` (the Forgeheart Wyrmling's `breathRange`) don't grow with level or gold; `breathRange` (%) stretches the breath's `range` in `StatCalc.resolveAbility`, and the breath VFX gets a matching `reach`.
- **Quest markers and the guide**: WorldView keys markers by giver model (a keeper inside a dungeon gets its own) and shows a grey ! for a quest locked only by level (`QuestUtil.lockedByLevel`). The quest guide (Waypoint) never points outside the dungeon you're in, skips "go to a dungeon" objectives unless you pick that quest, and picking the quest it's following turns it off (profile setting `questGuide`, via `SetSetting`).
- **Practice targets** belong to one player (`OwnerUserId`) and live in `workspace.PracticeTargets`. Nothing streams their motion: every client moves them with `RangeUtil.position`, and `CombatService.collectTargets(attacker)` adds the attacker's own targets (entries with `practice` set and a plain `{ Position }` root) from the same function. While the player attribute `RangeMode` is set, only Fireball works (server and client), on `Range.FIREBALL_COOLDOWN`.
- The user wants **distinctive dragons**, not a generic "AI dragon" look. Keep each class's silhouette unique, and keep the shared signature: the ember core, rune marks, scalloped two-part wings and the hinged jaw.
